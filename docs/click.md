# 单次点击执行链路

这一阶段把「可信观察」接到了「点击」上，并实现了真实的 Windows 鼠标
左键单击后端。**真实输入默认关闭**：只有配置和进程环境变量同时满足，
才会构造真实后端；否则生产环境登记的 `click_element` 在 `prepare()`
阶段就失败关闭，连授权卡片都不会弹。

- 已实现：输入后端抽象、`FakeInputBackend`、真实 `WindowsInputBackend`
  （`SendInput`）、`click_element` 工具、完整的授权与执行顺序、结果未知
  处理、工作流禁止自动重试、急停、服务端速率限制。
- 仍然只支持**单次左键单击**：没有键盘输入、双击、拖拽、滚轮或批量点击。
- 没有"真实后端不可用就自动换成另一种真实输入"的路径；构造失败就是没有
  后端，工具失败关闭。

代码位置：

- `app/input/backend.py`：后端接口、结果类型、窗口身份与安全界面判断
- `app/input/fake.py`：只记录、不执行的后端
- `app/input/windows_api.py`：`SendInput`、前台、窗口、安全桌面的底层封装
- `app/input/windows_backend.py`：真实后端与双重启用条件
- `app/input/control.py`：急停与速率限制
- `app/tools/click_tools.py`：`click_element`
- `app/api/input.py`：急停状态、触发与恢复接口
- `scripts/test_click_tool.py`：离线链路测试
- `scripts/test_windows_backend.py`：真实后端的离线测试（全部使用假适配器）
- `scripts/test_workflow_engine.py`：结果未知不重试、急停停止任务

真实后端的细节、启用方式和安全边界见 [windows-input.md](windows-input.md)。

## 一、模型能提交什么

只有两个参数：

| 参数 | 说明 |
| --- | --- |
| `observation_id` | 上一次 `inspect_screen` 返回的可信观察编号 |
| `element_id` | 那条记录里的元素编号（`e1`、`e2`……） |

模型**不能**提交屏幕坐标、窗口句柄、进程号或窗口标题。多写一个参数会被
`Tool.validate()` 直接拒绝。坐标和窗口身份全部由服务端根据观察记录取得。

## 二、确认前固定目标

`prepare()` 在用户看到确认卡片之前完成这些事：

1. 取回观察记录；不存在、过期、失效、整桌面观察、映射不可信都直接阻止。
2. 找到目标元素；编号不属于这条记录就阻止，并列出可用编号。
3. 检查目标窗口不是 UAC / 锁屏等安全界面。
4. 检查输入后端存在且可用；没有就失败关闭。
5. 检查当前不在安全桌面。
6. 做一次只读的观察记录校验。窗口已经移动/关闭/DPI 变化的记录，
   不会再去打扰用户确认。
7. 把 `observation_id`、`element_id`、窗口身份和记录中的矩形通过
   `Resolution.injected` 固定下来。

确认卡片会明确写出：

- 目标应用（进程名）
- 目标窗口（标题和 HWND）
- 目标元素（名称和类型）
- 坐标由服务端计算，模型没有指定坐标
- 本次会产生**真实鼠标输入**（后端启用时），不是模拟点击；
  后端名称也会一并显示
- 执行前会再次核对窗口身份、位置、前台和桌面安全，任何一项不符都会停止

## 三、执行顺序

用户确认之后，`run()` 按下面的顺序执行：

```
1. 急停是否已触发？                   是 -> 停止，不点击
2. 后端存在且可用？                   否 -> 失败关闭，不点击
3. 取回观察记录，核对确认前固定的目标   不一致 -> 停止
4. 目标不是 UAC / 安全桌面？           否 -> 停止
5. 观察记录校验（第 1 次）             失败 -> 停止
6. 后端聚焦目标窗口                    失败 -> 停止
7. 观察记录校验（第 2 次）             失败 -> 停止
8. 前台窗口身份核对                    不匹配 -> 停止
9. 再查一次安全桌面                    是 -> 停止
10. 发送前再查一次急停
11. 后端内部：再核对窗口、前台、桌面边界、急停和速率
12. 后端内部：确认坐标处最顶层的窗口仍是目标窗口
13. 后端点击服务端算出的物理坐标（部分提交时补发一次左键抬起）
14. 无论结果如何，主动失效这条观察记录
15. 如实报告 succeeded / failed / unknown
```

第 6、7、8 步是竞态处理的核心：聚焦本身可能移动窗口或切走前台，
所以聚焦之后必须把窗口身份、位置、尺寸、DPI 和坐标再核对一遍，
并且在点击前最后确认前台确实是目标窗口。

真实后端在真正 `SendInput` 之前还会把第 11 步完整做一遍。这些检查只能
缩短竞态窗口，不能证明竞态不存在。

**不能声称这些检查消除了竞态。** 它们只是把危险窗口缩到很小。
从"最后一次检查"到"真正按下鼠标"之间仍然可能有变化，因此后端还必须
自己再核对一次窗口身份和前台；真实后端接入后，这一点是强制要求。

## 四、结果状态

`ToolResult.outcome` 有三种值：

| 值 | 含义 | 工作流行为 |
| --- | --- | --- |
| `succeeded` | 后端确认点击完成 | 正常继续 |
| `failed` | 后端明确说没有点成功 | 记录失败；`retry_safe=False`，不自动重试 |
| `unknown` | 超时、异常、无法确认是否点上 | 停止并请用户确认后续处理，绝不自动重试 |

`unknown` 的文案会明确写：

> 结果未知。已停止，不会自动重试；请先确认目标程序现在的状态，再决定
> 是否重新查看屏幕并重新授权。

`click_element.retry_safe = False`。工作流引擎在执行失败后会先看这个
标记；即使错误文本里有「超时」「连接」这类通常会触发重试的词，也不会
再执行一次。`scripts/test_workflow_engine.py` 用真实工具和真实引擎守着
这一点。

## 五、失败关闭的各种情况

| 情况 | 发生阶段 | 是否点击 |
| --- | --- | --- |
| 用户拒绝授权 | 闸门 | 否 |
| 观察记录不存在 / 被伪造 | prepare | 否 |
| 观察记录过期 / 已失效 | prepare 或执行前 | 否 |
| 目标元素不存在 | prepare | 否 |
| 模型自己塞坐标 | 参数校验 | 否 |
| 窗口移动 / 关闭 / 最小化 | prepare 或第 1/2 次校验 | 否 |
| 聚焦后窗口身份变化 | 第 2 次校验 | 否 |
| 聚焦失败 | 聚焦 | 否 |
| 前台被别的窗口抢走 | 前台核对 | 否 |
| 坐标处被别的窗口遮挡 | 命中检查 | 否 |
| DPI / 屏幕度量变化 | 第 1/2 次校验 | 否 |
| 目标属于 UAC / 锁屏 | prepare 或执行前 | 否 |
| 执行时突然进入安全桌面 | 安全桌面检查 | 否 |
| 输入后端不存在 / 不可用 | prepare 或执行前 | 否 |
| 急停已触发 | prepare / 执行前 / 发送前 | 否 |
| 两次点击间隔不足 1 秒 | 占用速率额度 | 否 |
| 最近一分钟已达 5 次 | 占用速率额度 | 否 |
| 后端明确失败 | 点击 | 已尝试 |
| 后端结果未知 | 点击 | 可能已发生 |

所有失败都不会返回可执行的坐标。`unknown` 也不会被降级成 `failed`。

## 六、观察记录用一次就失效

调用后端点击之后（无论成功、失败还是未知），工具会主动把这条观察记录
标记为失效。原因很简单：点击会改变界面，旧截图里的元素位置不再可信。
下一次操作必须重新观察、重新确认。

失败发生在点击之前时，记录不一定失效；但如果窗口已经移动或 DPI 变化，
观察记录校验本身就会拒绝后续使用。

## 七、真实后端的契约

真实后端 `WindowsInputBackend` 遵守同一套 `InputBackend` 接口：

1. `status()`：可用性检查；不可用（非 Windows、DPI 读不到、急停生效等）
   时调用方失败关闭。
2. `focus_window()`：把窗口带到前台，并确认前台就是它；不接受模型给的
   身份，还会复核窗口可见性、最小化状态和位置。
3. `foreground_matches()`：点击前最后核对一次前台。
4. `click()`：只接受物理像素坐标；在真正 `SendInput` 前再核对窗口身份、
   前台、安全桌面、屏幕边界、急停、速率和坐标处的顶层窗口；部分提交时
   补发一次左键抬起（不是重试点击）；明确区分 `failed` 和 `unknown`。
5. `secure_desktop()`：用 `OpenInputDesktop` 等系统 API 检测 UAC / 锁屏；
   读不到或无法确认时按"安全桌面"处理，失败关闭。

以下约束在真实后端下仍然不变：

- `click_element.requires_confirmation = True`
- `click_element.requires_prepared_target = True`
- `click_element.retry_safe = False`
- 模型只能提交 `observation_id + element_id`
- 点击前至少两次观察记录校验
- 用户拒绝后立即停止

真实的 `SendInput` 只出现在 `app/input/windows_api.py`。工具、后端和
适配层之外的任何模块都不能调用它。

## 八、测试

```
.venv\Scripts\python.exe scripts\test_click_tool.py
.venv\Scripts\python.exe scripts\test_windows_backend.py
.venv\Scripts\python.exe scripts\test_workflow_engine.py
```

`test_click_tool.py` 走真实的 `gate.authorize_tool()`，用测试协程代替用户
点允许/拒绝；所有窗口、屏幕度量、时钟和输入都是假的。测试结束时还会
用 AST 检查点击链路源码里没有系统输入调用或自动化输入库。

`test_windows_backend.py` 用假的底层适配器覆盖双重启用、安全桌面、窗口
变化、负坐标、多显示器、速率限制、急停和三种结果映射；**不会发送任何
真实输入事件**。

`test_workflow_engine.py` 把真实的 `click_element` 接到工作流引擎上：
假后端返回 `unknown` 时确认只执行一次、不会自动再点；急停生效时确认
确认卡片不出现、工具不执行、整个任务立即停止。
