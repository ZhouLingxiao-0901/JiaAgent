# 真实 Windows 鼠标输入

这一阶段实现了真实的 Windows 单次鼠标左键单击，但**默认关闭**。开发、
测试和日常运行都不会因为代码存在就自动操作桌面。

范围严格限制为：

- 一次工具调用只发送一次左键单击（移动、按下、抬起三个事件）
- 不包含键盘、双击、拖拽、滚轮或批量点击
- 不通过模拟鼠标移动或发送窗口消息绕过授权
- 不支持非 Windows 环境

## 一、双重启用条件

只有下面两条**同时**满足，`build_input_backend()` 才会构造
`WindowsInputBackend`：

1. `config/tools.yaml`：

   ```yaml
   input:
     real_mouse_enabled: true
   ```

2. 真实进程环境变量：

   ```
   JIA_ENABLE_REAL_MOUSE=1
   ```

两个条件分别检查，缺一不可：

- 只改配置，没有环境变量 -> 不启用
- 只设环境变量，配置仍是 `false` -> 不启用
- 任何一条读不到或值不对 -> 不启用

没有启用时，工具登记处拿到的后端是 `None`。`click_element` 会在
`prepare()` 阶段失败关闭，连确认卡片都不会出现，也不会自动退回另一种
真实输入方式。

> `.env` 只是示例文件，应用不会因为它里面写了 `JIA_ENABLE_REAL_MOUSE=1`
> 就自动启用真实输入。必须由启动服务的真实环境显式设置。

网页和接口**不能**修改配置或环境变量，因此也不能通过请求把真实输入
打开。后端只在服务启动、登记工具时按条件构造一次。

## 二、坐标与多显示器

- 观察阶段记录的是归一化坐标，服务端根据可信观察记录和 DPI 换算成
  物理屏幕像素；模型不能提交坐标。
- 使用 `MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK`，把物理像素
  按**整个虚拟桌面**（而不是主显示器）映射到 `0..65535`。
- 支持负坐标和多显示器：虚拟桌面左上角可能不是 `(0, 0)`，例如左侧
  副屏可以是从 `-1920` 开始。
- 发送前会重新读取虚拟桌面度量并检查坐标是否落在
  `[virtual_left, virtual_top) - [right, bottom)` 内；越界直接拒绝。
- DPI 读取失败、屏幕度量不一致或无法确认时失败关闭。

## 三、执行前的核对

工具层已经完成授权、观察记录校验、聚焦和前台核对。真实后端在调用
`SendInput` 之前还会再查一遍：

1. 后端可用（Windows、DPI、屏幕度量正常）
2. 急停未触发
3. 不是 UAC / 安全桌面
4. 目标不是 UAC / 锁屏窗口（工具层查过，后端再查一次）
5. 目标窗口身份、可见性、最小化状态、位置和尺寸没有变化
6. 前台仍是目标窗口
7. 坐标仍在当前虚拟桌面范围内
8. 占用一次速率额度
9. 发送前最后再查急停、安全桌面、窗口和前台
10. 用 `WindowFromPoint` + `GetAncestor(GA_ROOT)` 确认坐标处最顶层的
    窗口**仍然是目标窗口**

第 10 步补上了一个盲区：前台是目标窗口，不代表目标坐标没有被别的
置顶窗口、弹窗或遮罩挡住。命中的子控件会通过 `GetAncestor` 归到它
所属的顶层窗口；无法确认、没有窗口或窗口不同，一律拒绝发送。

这些检查只能缩小竞态窗口，不能证明竞态不存在。

安全桌面检测使用 `OpenInputDesktop` + 桌面名称检查，并辅以前台进程
判断。任何读取失败、异常或无法确认的情况都按"不安全"处理，拒绝执行。

所有句柄相关的 Windows API 都显式声明了参数和返回类型（`HWND`、
`HDESK`、进程句柄），避免 64 位句柄被 ctypes 默认的 `c_int` 截断，
导致前台、桌面或进程身份核对比较了错误的值。

## 四、结果语义

| 结果 | 含义 |
| --- | --- |
| `succeeded` | `SendInput` 确认三个预期事件全部提交（移动、左键按下、左键抬起） |
| `failed` | 能明确确认没有执行：`SendInput` 返回 0 个事件，或发送前检查失败 |
| `unknown` | 无法确认是否执行：部分事件提交、适配层抛异常等 |

`unknown` 绝不会被降级成 `failed`，也绝不自动重试。观察记录在点击尝试
之后立即失效，用户必须重新观察、重新确认。

### 部分提交后的按键释放

`SendInput` 按顺序插入事件。如果只提交了前两个事件，"左键按下"已经
生效但"左键抬起"没有，鼠标会停留在按下状态。适配器在这种情况下会
**补发一次只包含 `LEFTUP` 的事件**：

- 这不是重试点击：不会移动、不会再次按下、不会产生第二次单击
- 释放成功：结果仍是 `unknown`，原因里说明已补发抬起
- 释放失败：结果仍是 `unknown`，并明确提示
  「鼠标左键可能仍处于按下状态，请立即人工检查」
- `SendInput` 抛异常时状态未知，也会尝试一次释放（按键若本来没按下，
  抬起是无害的）；释放失败同样提示人工检查

只提交了移动事件（`inserted == 1`）时左键没有按下，不会补发抬起。

## 五、急停

急停是全局的、持久的：

- 用户可从聊天界面右上角的「急停」按钮触发
- 触发后写入 `data/input_emergency_stop.json`，服务重启后会重新读回
- 工具在 `prepare()`、`run()` 和真正发送前都会检查
- 工作流在每一步申请确认之前检查；急停生效时不会弹确认卡片，整个任务
  立即停止，剩余步骤标记为跳过
- 触发时还会取消所有等待中的确认，避免用户在急停后继续批准点击
- 模型和工作流没有清除急停的入口

恢复必须由用户在界面上显式确认，而且**`confirmed: true` 本身不是授权**：

1. 页面先向 `POST /api/input/emergency-reset/prepare` 换取一次性挑战；
2. 用户在确认框中确认后，前端把 `{"confirmed": true, "nonce": "..."}`
   发给 `POST /api/input/emergency-reset`；
3. 服务端要求请求来自同源页面、带有有效本地会话，并且挑战未过期、
   未使用、属于该会话、急停代次在期间没有变化。

挑战有效期 60 秒，只能用一次；再次急停会让已签发的挑战立即失效。
检查和清除在同一个锁里完成，所以“确认之后又按下急停”时，恢复请求
会失败，新的急停一定会保留。恢复急停**不等于**启用真实输入：双重
启用条件仍然要满足，而且后端只在启动时按条件构造。

急停只影响真实输入；模拟后端和只读工具不受影响。

接口（全部挂在 `/api` 下）：

| 方法 | 路径 | 访问条件 | 说明 |
| --- | --- | --- | --- |
| `POST` | `/input/session` | 同源页面 / 本机请求 | 签发 30 分钟本地会话令牌 |
| `GET` | `/input/status` | 会话令牌 | 启用条件、后端类型、急停状态、速率额度 |
| `POST` | `/input/emergency-stop` | 同源页面 / 本机请求（**不要求令牌**） | 立即急停，并取消等待中的确认 |
| `POST` | `/input/emergency-reset/prepare` | 会话令牌 | 换取一次性恢复挑战 |
| `POST` | `/input/emergency-reset` | 会话令牌 + 一次性挑战 | 恢复急停；不会启用真实输入 |

急停故意不要求会话令牌：令牌过期或页面尚未初始化时，用户仍然必须
能立刻停下。这是“减少能力”的动作，来源校验仍然生效。取舍是同源页面
或本机非浏览器请求可以反复触发急停，最坏结果是真实输入持续不可用
（拒绝服务），不会提升任何权限；跨站页面会被来源校验拒绝。

## 五之二、本地 HTTP 访问边界

服务默认只绑定回环地址。`run.py` 在启动前检查 `JIA_HOST`，不是
`localhost` / `127.0.0.0/8` / `::1` 就直接拒绝启动；应用层中间件还会
再检查一次 Host 和连接来源 IP，即使有人绕过启动脚本把服务绑到
`0.0.0.0`，局域网客户端也会收到 403。

此外：

- 没有启用 CORS，也不会返回 `Access-Control-Allow-Origin`；
- 非只读的 `/api` 请求必须来自同源页面：校验 `Sec-Fetch-Site`
  （只允许 `same-origin` / `none`）以及 `Origin`（没有时退回 `Referer`），
  协议、主机、端口都要和当前服务一致；
- `X-Jia-Session` 是自定义请求头，跨站页面要带它必须触发 CORS 预检，
  而服务不支持预检，所以即使偷到令牌也无法从别的网站直接使用；
- 会话和挑战只存在内存里，服务重启即失效；急停状态仍从磁盘读回。

**威胁模型：** 这些措施防的是别的网站（CSRF、DNS rebinding）和局域网
访问，也能拒绝过期、伪造、重放的恢复请求。它们**不是身份认证**，挡不住
同一用户权限下的恶意本地进程——那个进程可以自己申请会话、读取页面持有
的令牌，或者直接改配置、调用系统 API。不要把这套机制当成操作系统级
隔离。

急停没有使用全局键盘钩子，也没有常驻后台的输入监听。

## 六、速率限制

服务端统一执行，前端无法绕过：

- 两次真实点击至少间隔 **1 秒**
- 每分钟最多 **5 次**
- 每次工具调用最多一次左键单击

`input.min_click_interval_seconds` 和 `input.max_clicks_per_minute` 只能
把限制调得更严格，不能放宽到 1 秒 / 5 次以下。超限直接拒绝，不排队、
不拆分、不重试。

## 七、失败关闭

以下情况一律不发送输入：

- 非 Windows，或底层 API 不可用
- DPI / 屏幕度量读不到或前后不一致
- 无法可靠判断是否处于安全桌面
- 后端未启用、构造失败
- 急停已触发
- 速率超限
- 窗口关闭、隐藏、最小化、移动、改尺寸或换了进程
- 焦点没有成功切换，或前台被别的窗口抢走
- 坐标越界

## 八、测试

```
.venv\Scripts\python.exe scripts\test_windows_backend.py
.venv\Scripts\python.exe scripts\test_click_tool.py
.venv\Scripts\python.exe scripts\test_workflow_engine.py
.venv\Scripts\python.exe scripts\test_input_access.py
```

`test_windows_backend.py` 使用假的底层适配器、假窗口和可注入的时钟，
覆盖双重启用、安全桌面、窗口变化、负坐标、多显示器、速率限制、急停、
坐标命中检查、部分提交后的左键释放和三种结果映射。适配器级测试注入
假的 `user32`，验证桌面名称判断、句柄关闭、`SendInput` 回执解释和
ctypes 原型。

`test_input_access.py` 用进程内的最小 ASGI 客户端直接调用输入路由
（不监听端口、不启动应用生命周期），覆盖 Host / 来源 IP / Origin /
`Sec-Fetch-Site`、跨站请求、会话缺失/伪造/过期、一次性挑战的过期与
重放、会话与代次绑定、并发急停优先，以及恢复后真实输入仍然关闭。
**所有测试都不会发送真实输入事件。**

另有 AST 检查确保只有 `app/input/windows_api.py` 调用 `SendInput` 等
底层输入接口，且没有引入 `pyautogui` / `pydirectinput` / `pynput` 之类
的自动化输入库。
